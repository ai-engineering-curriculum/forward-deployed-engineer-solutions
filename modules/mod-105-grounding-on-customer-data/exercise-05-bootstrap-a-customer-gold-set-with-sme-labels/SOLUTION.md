# exercise-05 — Bootstrap a Customer Gold Set with SME Labels · Reference Solution

## 1. Solution overview

The deliverable is a **repeatable process + runnable scaffolding** for
building a **customer-specific gold evaluation set** that measures the
grounded-retrieval + generation pipeline from exercises 01–04 against
*this customer's* questions, *this customer's* corpus, and *this
customer's* subject-matter experts (SMEs).

Four principles:

1. **Questions come from the customer, not the FDE.** A gold set
   seeded from your head measures your taste. A gold set seeded from
   real user questions measures the product.
2. **SMEs label, FDEs facilitate.** SMEs have the domain truth; the
   FDE's job is to turn their disagreements into a labeling spec
   and their time into measurable throughput, not to arbitrate
   content.
3. **Labels cover what the pipeline can fail at**, not just what is
   easy to label: correct answer, cited documents, must-deny probes
   (exercise-02), must-not-leak PII probes (exercise-03),
   must-render-as-no-evidence (exercise-04), and freshness
   expectations.
4. **The gold set is a living artifact.** It version-bumps with the
   corpus. A gold set frozen at pilot start lies within weeks. The
   plan includes a cadence for triage and retirement.

A good bootstrap produces, in 2–4 weeks with ~3 SMEs, a gold set of
**120–300 labeled items** that is representative, stratified, and
usable in CI (see mod-107 for the harness).

The common FDE mistake is to spend weeks on a "comprehensive" taxonomy
before any label exists. Start with a thin, stratified cut; label it;
iterate. Breadth is cheap once the labeling schema is right.

## 2. Worked implementation

### 2.1 Phases and timeline

| Phase | Weeks | Output |
|---|---|---|
| **P0 — Scope** | 0.5 | Use-case list, strata, target counts, SME time budget |
| **P1 — Seed** | 1 | 30–60 seed items (half real-user, half SME-authored) |
| **P2 — Label** | 1–2 | Full labels with references + inter-annotator agreement |
| **P3 — Bake-off** | 0.5 | Dry-run against current pipeline; triage top failures |
| **P4 — Promote + maintain** | ongoing | Gold set in repo; weekly triage; quarterly refresh |

### 2.2 Strata — what the gold set must span

A gold set of 200 items means little if 180 are easy lookup. Stratify
on failure modes the pipeline can actually experience:

| Stratum | Why | Target share |
|---|---|---|
| **S1 — Factual lookup** | "What is X?" answerable from one chunk. Calibrates retrieval recall. | 25% |
| **S2 — Multi-doc synthesis** | Answer requires 2–4 chunks across documents. Tests fusion/rerank and prompt length. | 20% |
| **S3 — Numeric / dated** | "How many …" / "What is the current rate" / "As of today." Tests freshness (ex-04). | 15% |
| **S4 — ACL-sensitive** | Same question across users with different access; different answers required (ex-02). | 10% |
| **S5 — Must-deny** | Caller has no access; correct answer is "no evidence I can show you." | 10% |
| **S6 — PII-sensitive** | Answer must use pseudonyms or redact (ex-03). | 5% |
| **S7 — Stale-source** | Correct chunk exists but is past freshness policy; answer must flag staleness. | 5% |
| **S8 — No-evidence** | No chunk answers the question at all; correct answer is the designed empty state. | 5% |
| **S9 — Prompt-injection in corpus** | Retrieved chunk tries to manipulate the model (OWASP / ATLAS). Must be ignored. | 5% |

Numbers are starting points; adjust with the customer. The point is to
**force the labeling plan to include strata the pipeline will
otherwise fail at silently**.

### 2.3 Seeding — where real questions come from

Order of preference:

1. **Support / helpdesk transcripts.** Real questions, already in
   natural language, already labeled by outcome. De-identify first
   (reuse the pseudonymisation pipeline from exercise-03) before
   they leave the ticketing system.
2. **Shadow-logged user queries from a POC.** Only with explicit
   opt-in; otherwise you are measuring on data you promised was
   ephemeral.
3. **SME-authored questions targeting each stratum.** SMEs write a
   small batch per stratum as a prompt ("Give me five S3-shaped
   questions you ask Slack weekly"). These fill coverage gaps but
   are not a substitute for real-user data.
4. **Synthetic questions generated by an LLM over the corpus.** Use
   sparingly to fill strata the SMEs cannot cover. Every synthetic
   question requires SME review before it joins the set — synthetic
   questions trained on a bad corpus produce a biased gold set.

Deduplicate semantically (embed + cosine threshold, SME-reviewed)
before labeling starts.

### 2.4 Labeling schema (per item)

Every gold item is a row in a repo-tracked file (JSONL or CSV; JSONL
preferred). Minimal, but complete:

```jsonc
{
  "id": "G-000142",
  "version": "2026.11",
  "stratum": "S2",
  "question": "What is our current refund policy for enterprise contracts?",
  "caller_persona": "acct-exec-finance-us",           // see §2.5
  "expected": {
    "evidence_state": "grounded",                      // grounded|partial|missing
    "must_cite_any": ["doc:policies/refunds-enterprise-v7",
                      "doc:policies/refunds-mcl"],
    "must_not_cite": ["doc:policies/refunds-consumer"],
    "must_mention":  ["30-day", "SLA credit", "enterprise plan"],
    "must_not_mention": ["consumer", "promo code"],
    "allow_freshness_days": 90,                        // per S3/S7
    "must_render_pseudonym_types": [],                 // per S6
    "must_deny": false                                 // per S5
  },
  "sme_notes": "The MCL version supersedes the enterprise-v7 for FY26.",
  "labeled_by": ["sme-1","sme-3"],
  "label_confidence": "high",                          // high|medium|low
  "labeled_at": "2026-11-18T13:04:00Z",
  "retired_at": null,
  "retired_reason": null
}
```

Field notes:

- `caller_persona` encodes the identity + residency + classification
  ceiling (see exercise-02). Must-deny items need a persona who
  cannot read the required docs; ACL-sensitive items need multiple
  persona variants.
- `must_cite_any` is a set-of-sets if alternative valid sources
  exist; keep the structure flat unless the customer's content has
  this shape.
- `must_mention` and `must_not_mention` are **conservative, exact
  lexical** expectations — enough to decide pass/fail in CI without
  an LLM judge. LLM-as-judge is optional (§2.7) and subordinate.
- `label_confidence` surfaces on the labeling UI and in the report;
  low-confidence rows are not used as pass/fail blockers.

### 2.5 Personas

A persona is the shape of a caller the retriever sees (per
exercise-02):

```jsonc
{
  "id": "acct-exec-finance-us",
  "principal": "user:persona+acct-exec-finance-us@acme.test",
  "groups": ["group:sales-us", "group:finance-us", "group:all-employees"],
  "tenant_id": "acme",
  "residency": "us-east",
  "classification_ceiling": "Internal"
}
```

Rules:

- Personas are **real tokens** in the fixture tenant; the retriever
  cannot tell the difference between a test persona and a real
  user. This keeps the eval honest.
- Minimal persona set to cover strata S4 + S5: owner, cross-team
  reader, outsider, restricted.
- Personas rotate on the customer's SSO rotation cadence; don't
  wire them to permanent credentials.

### 2.6 Running labeling with SMEs

Operational design:

- **Pair labeling for the first 20 items.** Two SMEs label
  independently, review disagreements, write one line each to the
  "labeling spec" explaining the rule. This produces the spec your
  future labelers follow.
- **Time-box per item.** 4–6 minutes average. If an item takes
  longer than 15 minutes, park it — the ambiguity is a labeling
  spec problem, not an SME problem.
- **Keep SMEs out of the tool.** A simple spreadsheet or lightweight
  web form (see §2.8 sketch) with a fixed field list beats a
  bespoke labeling UI. The time savings are in reducing context
  switches, not in building software.
- **Reconcile weekly.** Disagreements go into a triage bucket;
  the FDE + SME lead resolve, update the labeling spec, and
  re-run disputed items.
- **Report inter-annotator agreement** per stratum, not globally.
  Lower agreement on S2 / S4 is expected and informative.

### 2.7 CI harness (hand-off to mod-107)

The gold set drives a regression suite. Minimal contract:

```python
# eval/score_item.py (sketch)
from typing import Dict, List

def score(item: Dict, pipeline_output: Dict) -> Dict:
    expected = item["expected"]
    # Cited = only sources referenced by at least one claim, not every
    # retrieved source. `claims[].citations` holds source ids ("c1",
    # "c2", ...) that resolve to `sources[].id → doc_id`. Scoring on
    # `sources` alone would pass must_cite_any whenever the required
    # doc was merely retrieved, and fail must_not_cite on unused
    # retrieval candidates.
    source_to_doc = {s["id"]: s["doc_id"]
                     for s in pipeline_output.get("sources", [])}
    cited_ids    = {cid for claim in pipeline_output.get("claims", [])
                        for cid in claim.get("citations", [])}
    cited        = {source_to_doc[cid] for cid in cited_ids
                                        if cid in source_to_doc}
    text         = pipeline_output.get("answer", "").lower()

    checks: List[Dict] = []

    # evidence state
    checks.append({
        "name": "evidence_state",
        "pass": pipeline_output.get("evidence_state") == expected["evidence_state"],
    })

    # must_cite_any
    if expected["must_cite_any"]:
        checks.append({
            "name": "must_cite_any",
            "pass": bool(cited & set(expected["must_cite_any"])),
        })

    # must_not_cite
    if expected["must_not_cite"]:
        checks.append({
            "name": "must_not_cite",
            "pass": not (cited & set(expected["must_not_cite"])),
        })

    # must_mention / must_not_mention (exact lexical)
    for term in expected.get("must_mention", []):
        checks.append({"name": f"must_mention:{term}",
                       "pass": term.lower() in text})
    for term in expected.get("must_not_mention", []):
        checks.append({"name": f"must_not_mention:{term}",
                       "pass": term.lower() not in text})

    # must_deny (no sources shown)
    if expected.get("must_deny"):
        checks.append({"name": "must_deny",
                       "pass": not pipeline_output.get("sources")})

    # freshness policy (per S3/S7)
    allow = expected.get("allow_freshness_days")
    if allow is not None:
        max_age = pipeline_output.get("freshness", {}).get("max_age_days", 0)
        checks.append({"name": "freshness_within_policy",
                       "pass": max_age <= allow})

    return {
        "id": item["id"],
        "stratum": item["stratum"],
        "label_confidence": item["label_confidence"],
        "checks": checks,
        "pass": all(c["pass"] for c in checks),
    }
```

Reporting:

- **Per-stratum pass rate**, not only aggregate. A 90% aggregate
  that is 100% on S1 and 60% on S5 is a release-blocking report.
- **Low-confidence items excluded** from release gates; they still
  show on the dashboard.
- **LLM-as-judge is optional.** For long-answer items where exact
  lexical checks are too strict, add an LLM-judge check behind a
  flag. Keep the deterministic checks as the primary signal; the
  judge is advisory.
- **Trend over time.** The gold set is used weekly against the
  live pipeline (see mod-110); regressions are triaged within an
  SLA the customer sets.

### 2.8 A lightweight labeling form (optional)

If a spreadsheet does not fit the customer, a 100-line Streamlit /
Gradio app is enough. The fields match §2.4; the app writes JSONL
to a repo. Keep the UI dumb:

- One item per screen.
- Rich preview of the top-k retrieved chunks for the current
  pipeline so the SME can decide if the retrieval is even plausible.
- No auto-save of partial labels; SME submits or discards.
- All writes include the SME's identity and timestamp for audit.

### 2.9 Maintenance — the part everyone skips

A gold set rots when:

- The corpus changes (new policies supersede labeled ones).
- SMEs rotate (institutional knowledge leaves with them).
- The product scope expands (new strata appear).

Cadence:

- **Weekly triage** — 30 minutes, FDE + SME lead, look at the
  previous week's regressions and newly failing items; retire or
  re-label as needed.
- **Monthly refresh** — add 10–20 items from the past month's user
  queries.
- **Quarterly audit** — retire items whose cited sources no longer
  exist, bump `version`, rerun inter-annotator agreement on a
  random 5% sample.

Retirement is first-class: set `retired_at` and `retired_reason`;
keep the row for history. Deleted gold items should not silently
disappear from the trend line.

### 2.10 What this exercise is not

- **Not a safety-eval replacement.** A customer gold set measures
  grounded correctness. Safety evals (jailbreak resistance, policy
  compliance) are a separate program (mod-108). A single set that
  tries to be both is weaker at each.
- **Not a leaderboard.** Do not publish to anyone outside the
  customer team; gold items commonly contain customer-specific
  content.
- **Not a substitute for live metrics.** Thumbs-up / correction
  rates in production are the ultimate signal; the gold set is the
  pre-merge gate.

## 3. Validation steps

1. **Representativeness review.** The SME lead confirms the strata
   split matches the use case; adjust targets before labeling
   scales up.
2. **Inter-annotator agreement.** Report Cohen's kappa (or simple
   percent agreement + disagreement breakdown) per stratum on the
   first 40 double-labeled items. Target per-stratum kappa ≥ 0.6
   before accepting single-annotator labels on that stratum.
3. **Spec dry-run.** A new labeler not involved in the seed can
   label 10 items using the spec alone and reach the same answers
   as the original pair on ≥ 8 of 10. If not, the spec is
   under-specified.
4. **CI dry-run.** Run the harness against the current pipeline;
   confirm pass/fail decisions match SME expectations on a
   stratified 20-item sample.
5. **Persona verification.** Each ACL-sensitive item uses a
   persona that is actually denied in the index (see exercise-02
   RLS/filter), not a persona that looks denied.
6. **PII canaries.** For S6 items, confirm cleartext never appears
   in the pipeline output; the pseudonymised form is the correct
   expected answer (reuse exercise-03 §3.2 canary approach).
7. **Rollback test.** Flip the pipeline to a known-worse
   configuration; confirm the gold set catches the regression
   on the expected strata.
8. **Documentation.** `GOLD_SET.md` in the repo describes the
   schema, strata, target counts, labeling spec, personas, and
   maintenance cadence. A new FDE can onboard without a meeting.

## 4. Rubric / review checklist

Score 0–2 per row. 16/24 passes before the gold set gates releases.

| Dimension | 0 — Missing | 1 — Partial | 2 — Strong |
|---|---|---|---|
| Real-user seeding | Only FDE-authored | Mix, no de-id | Real tickets de-identified + SME authored |
| Stratification | Flat list | Named strata, no targets | Named strata with target shares and persona mapping |
| Labeling schema | Freeform text | Minimal fields | Full §2.4 schema with must-cite / must-deny / freshness |
| Persona coverage | Single user | Owner + outsider | ≥ 4 personas including must-deny |
| Inter-annotator agreement | Not measured | Global only | Per-stratum, with target thresholds |
| Labeling spec | None | Draft | Published spec; new labeler passes dry-run |
| CI harness | Hand runs | Deterministic checks only | Deterministic + per-stratum reporting + optional LLM-judge |
| Freshness in labels | Not encoded | Flag only | `allow_freshness_days` per S3/S7 item |
| PII probes | Absent | Mentioned | S6 items with pseudonym-expected labels |
| Must-deny probes | Absent | Few | S5 items with persona + expected empty-state |
| Prompt-injection probes | Absent | None | S9 items drawn from OWASP ML Top 10 / MITRE ATLAS tactics |
| Maintenance cadence | None | Ad hoc | Weekly / monthly / quarterly cadences documented and running |

## 5. Common mistakes

- **Boiling the ocean.** A 500-item taxonomy before any label
  exists burns SME goodwill. Start with 30–60 seeds; iterate the
  spec from disagreements.
- **FDE-authored questions.** Measures the FDE's intuition, not
  the product. Pay for the extra process cost of using real
  user data; it is worth it.
- **All S1 lookup items.** The pipeline is going to fail on S2,
  S4, S5, S9; without those strata the eval hides the failures.
- **LLM-as-judge as the primary signal.** Judges drift between
  model versions and tenants. Keep deterministic checks as the
  gate; use the judge where exact lexical fails.
- **Must-mention lists that are too tight.** The pipeline
  rephrases correctly and fails the check. Prefer short, factual
  anchors ("30-day", "SLA credit") over sentence-shaped assertions.
- **Personas that are not actually denied.** An S5 persona who
  can see the expected doc in the source system makes the test
  meaningless. Verify via exercise-02 filters.
- **Gold set frozen at pilot start.** Corpus churn makes labels
  stale; weekly triage is cheap compared to the cost of a false
  "regression."
- **No per-stratum reporting.** A 90% aggregate pass can hide a
  S5 regression that is a release blocker.
- **Mixing safety evals in.** A set that tries to measure
  grounded correctness **and** jailbreak resistance ends up weak
  at both. Keep them separate; see mod-108.
- **No audit of the labeling workflow.** Who labeled what,
  when, under which spec version — if the customer asks in a
  review, the answer should be in the repo, not in an SME's head.
- **Synthetic-only questions.** LLM-generated questions trained
  on a biased corpus produce a biased gold set. Treat synthetic
  as fill, not foundation.
- **One-shot inter-annotator agreement.** Measure once, forget
  forever. Quarterly re-measurement catches drift as SMEs rotate.
